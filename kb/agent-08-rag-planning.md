# Agent 开发 08：Agentic RAG 与多步检索设计

整理日期：2026-09-15。本文给出在现有知识库问答之上的设计练习，并非宣布 StudyPilot 已具备这些能力。

## 固定 RAG 与 Agentic RAG
固定 RAG 通常按既定路径检索后生成；Agentic RAG 将是否检索、查什么、是否补查交给模型在边界内决定。官方检索文档讨论了将搜索作为工具提供给 Agent 的方式。选择哪种方式应看任务复杂性、可预测性与额外延迟是否值得。
来源：[LangChain Retrieval](https://docs.langchain.com/oss/python/deepagents/retrieval)。

## 复杂问题怎么拆成检索子问题
建议先识别问题中的对象、关系、时间和约束。例如“对比工具幂等与检查点恢复”需要分别找到两者定义，再检索它们在故障恢复中的交互。不要把宽泛问题直接重复搜索十次。可以记录已查询的子问题、已覆盖证据和仍然缺失的信息，并限制补查轮数。

## 查询改写不能改变用户意图
建议保留术语原文、错误码、版本号和否定条件。改写可以补同义词，不能把“1.1 版本如何实现”变成“最新版本有什么”。对于不明确的产品名或用户私有背景，应先说明需要澄清的部分；模型自己猜出来的公司、版本和日期不能成为检索事实。

## 怎样判断证据足够回答
建议检查证据是否覆盖具体问题，而不只是主题相近。讲 Redis 的笔记不能推出用户公司某天故障的根因。答案需要多个证据点时，分别确认来源和适用条件；缺少某个点就明确说明，不应以一个高相似度片段代替全部证据。对于时效性问题，还要检查资料时间。

## 检索指标与答案指标分开
文档级 Hit@5 表示前五个片段中至少出现一个目标文档，不能证明命中了正确章节。建议另外标注应出现的证据片段，并检查答案中的结论是否受到这些片段支持。不要将无答案问题混入只支持正例的文档命中统计后宣称拒答准确率；拒答需要独立定义正负例与指标。

## StudyPilot 的练习路线
先把现有 retrieve 方法封装成只读工具，保持数据权限不变。让模型最多尝试少量补查并记录轨迹；遇到主题相关但无具体证据的问题，应返回资料不足。用固定 RAG 作为对照，比较证据覆盖、误答、延迟和费用，确认收益后再决定默认使用哪条路径。
