# 分布式事务与消息队列笔记

## 一、为什么需要消息队列

消息队列（MQ）解决三个核心问题：
- 解耦：生产者不需要知道消费者的实现，上下游独立演进；
- 削峰：突发流量先进入队列，消费者按自身能力消费；
- 异步：非核心链路（发通知、写日志）异步执行，缩短主链路响应时间。

## 二、Kafka 基本概念

- Broker：一台 Kafka 服务器；
- Topic：消息的逻辑分类；
- Partition：Topic 的分区，是并行与有序的最小单位；
- Offset：消息在分区内的位置，消费进度靠它记录；
- Consumer Group：组内消费者共同消费一个 Topic，同一分区只会被组内一个消费者消费。

## 三、消息可靠性（不丢消息）

生产端：ack=all 等待所有副本确认；发送失败重试。
存储端：副本数 ≥ 2，min.insync.replicas 保证至少同步副本数。
消费端：关闭自动提交，业务处理成功后再手动提交 offset（at-least-once）。

## 四、幂等与分布式事务

MQ 默认 at-least-once（可能重复投递），所以消费者要幂等：
- 用唯一业务号去重（数据库唯一索引 / Redis setnx）；
- 状态机校验：只有合法状态流转才处理。

分布式事务常见方案：
- 本地消息表 + 定时任务补偿；
- 事务消息（RocketMQ half message）；
- 最终一致 + 对账，是绝大多数业务的可接受方案；强一致用 TCC/Seata 但成本高。

## 五、消费积压怎么办

- 先扩容消费者实例；
- 快速失败跳过脏数据，事后补偿；
- 紧急时直接写离线表再异步回放，避免阻塞在线链路。
