# Agent 开发 06：多 Agent 协作、任务边界与合并

整理日期：2026-09-15。多 Agent 是可选的任务组织方式，不是项目高级程度的标志。

## 哪些任务适合并行 Agent
Anthropic 的研究系统采用主 Agent 协调多个研究子任务。独立方向可并行探索，各自上下文再压缩成结果给主 Agent；代价是更多调用和协调成本。强依赖同一上下文、需要频繁相互修改结果的任务，不一定适合拆成多个 Agent。官方报告的收益属于其内部场景，不能直接当成本项目的预期提升。
来源：[Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)。

## 给子任务写什么契约
建议每个子任务至少包含 goal、scope、inputs、allowedTools、budget、outputSchema、acceptanceCriteria。比如让两个子任务分别查工具安全与记忆管理，约定各自交付来源、结论和不确定性。不要只分配“研究一下”，否则任务范围会漂移，也难判断何时结束。

## 如何避免多个 Agent 修改同一文件
建议由主执行器分配互斥文件范围或独立工作区，明确谁负责合并。同一文件必须多人修改时，采用版本校验、补丁审查或显式串行阶段。共享文件系统并不等于冲突能自动解决。只读研究可并行，影响同一状态的写操作应按依赖和权限安排。

## 合并结论不能只拼接摘要
建议要求每个结论带来源定位与证据，主 Agent 检查重复、冲突、缺失项和时间范围。两个 Agent 同意同一结论，也可能是引用了同一个错误来源；投票不能替代证据检查。对于不同定义或不同版本造成的冲突，应保留适用条件，而不是强行取一个答案。

## 对照实验与退出条件
建议保持模型、语料和任务集尽可能一致，比较单 Agent 与多 Agent 的完成率、总 token、尾部延迟和人工返工量。子任务超时应产生部分结果或明确失败，由主执行器决定是否继续；总预算要覆盖全部子任务，而不是每个子 Agent 都拥有无限预算。
