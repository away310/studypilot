# Agent 开发 09：评测、运行轨迹与成本观测

整理日期：2026-09-15。评测应检查最终结果，也应检查执行过程是否遵守约束。

## 什么样的 Agent 评测才有效
官方评测文章区分了代码判定、模型判定和人工判定：可确定的结果优先程序检查，开放式质量可使用带规则的模型评分，再由人工校准。任务成功应以交付物或真实状态为依据。测试程序本身也可能写错，因此要准备能通过的参考解和能明确失败的反例。
来源：[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

## pass@k 与 pass^k 的区别
pass@k 关注 k 次尝试中至少一次成功；pass^k 关注 k 次全部成功。前者随尝试次数增多通常更容易达到，后者要求持续可靠。在独立且每次成功概率为 p 的简化假设下，至少一次成功为 1-(1-p)^k，全部成功为 p^k；真实运行可能并不独立，不能把该简化公式直接当作测量结果。
来源：[Agent evaluation metrics](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

## 建议记录的运行轨迹
建议记录 runId、stepId、模型标识、提示模板版本、工具名、脱敏参数摘要、开始结束时间、状态和错误类别。保留能解释行为的工具请求与结果，不要求存储模型私有思考过程。不同模型阶段和外部工具阶段分别记录耗时，便于区分检索慢、模型慢和依赖服务慢。

## 成本与稳定性如何一起看
建议至少观察任务完成率、首次响应时间、总耗时、P95 延迟、模型调用次数、工具重试次数以及实际 token 用量。实际账单与按标价估算要分开；不要硬编码长期不变的价格。成功率相同的方案仍可能在成本和失败恢复体验上差别很大。

## 为学习助手准备正例与反例
建议的正例包括查找概念、比较两份材料和按证据解释；反例包括同主题但没有具体事实、明显越权的工具请求和网络超时。还要测试不需要调用工具时能否直接完成。更换模型、提示模板或语料后，保留一组未参与调参的题目作验证，避免对自己出的题过拟合。
