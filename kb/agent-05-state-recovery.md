# Agent 开发 05：检查点、断点恢复与人工审批

整理日期：2026-09-15。长任务需要可恢复状态，不能只依赖一条一直保持的 HTTP 连接。

## 检查点解决什么问题
LangGraph 的 checkpointer 保存 thread 范围内的状态，持久化存储使中断后继续任务成为可能。检查点保存并不自动让外部副作用变成“恰好执行一次”。数据库状态与外部服务操作之间仍需要应用设计一致性边界。
来源：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。

## interrupt 恢复时会重新运行节点
LangGraph 的 interrupt 可以暂停任务，等待通过 Command(resume=...) 提供输入。恢复时所在节点会从头运行，因此 interrupt 之前的代码可能再次执行。不要用宽泛的 try/catch 吞掉中断控制信号；生产环境要使用持久化 checkpointer，并用正确的 thread_id 定位运行状态。
来源：[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。

## 为什么审批前不能先执行转账或发消息
这是针对有副作用节点的设计建议：先生成待审批操作的摘要与稳定标识，持久化，再暂停；审批通过后执行写操作。审批记录应绑定操作参数或其摘要，参数改变后重新判断是否需要审批，不能把一次同意复用到不同动作。审批前的节点重放不应造成重复写入。

## 幂等与事务边界
建议为每个写动作生成稳定的 operationId，在执行记录中保存状态和外部结果标识。外部服务已成功、应用还未来得及保存检查点时，恢复逻辑先查 operationId 的执行结果。若外部服务不支持幂等，则需要补偿、人工核对或专门的可靠投递设计，而不是把失败当成未执行。

## 如何验证真正可以恢复
建议让测试在三个位置主动中断：审批前、外部操作完成后、检查点保存后。重启运行器，验证授权仍然有效、同一操作没有重复执行、任务能给出明确状态。只在页面刷新后继续显示旧消息，不能证明执行器具备断点恢复能力。
